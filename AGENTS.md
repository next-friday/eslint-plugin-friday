# Repository Guidelines

## Agent Guidelines

- **Command Authority**: Read-only inspection and non-mutating verification commands needed to complete a requested task are permitted. Dependency installation, network-dependent commands, destructive commands, Git writes, publishing, and external mutations require explicit authorization.
- **Diagnostics & Reporting**: Report the exact scope and checks that actually ran. Distinguish verified results from assumptions. Do not report Git hooks or CI as local successes.
- **Working-Tree Authority**: Explicit current user requirements come first. Otherwise inspect the current working tree immediately before editing; do not infer current behavior from memory or Git history.
- **History Boundary**: Do not inspect Git history during ordinary audits or implementation work unless explicitly requested.
- **Rule Preflight**: Before editing, identify affected paths and read the applicable repository rules below.
- **Documentation Audiences**: Package guidance lives in [README.md](README.md), rule documentation in [docs/rules/](docs/rules/), and contributor guidance in [CONTRIBUTING.md](CONTRIBUTING.md). AI agent context and skills are indexed in [`.agents/docs/index.md`](.agents/docs/index.md) and [`.agents/skills/`](.agents/skills/).
- **Workflow Pointers**: PRs → [CONTRIBUTING.md](CONTRIBUTING.md), releases → [`.changeset/README.md`](.changeset/README.md), architecture → [`.agents/docs/architecture.md`](.agents/docs/architecture.md), rule-contract vocabulary → [CONTEXT.md](CONTEXT.md).

## Always-On Invariants

- **Direct & Minimal**: YAGNI and SSOT first. Prefer one concrete implementation over speculative wrappers, registries, generators, or fallback branches.
- **Platform First**: Native APIs and standard ecosystem tooling before new dependencies.
- **Stable Rule Names**: Exported rule names and observable rule behavior are public contracts. Renames or removals require explicit breaking-change intent.
- **Plugin Contract**: This repository owns Next Friday rule implementations, metadata, schemas, diagnostics, fixes, documentation, and the public plugin entrypoint.
- **Sibling Symmetry**: Public rules should use consistent naming, metadata, documentation, tests, and file structure unless a verified technical requirement requires a difference.
- **TypeScript First**: Author source and executable/configuration code as `.ts` when the owning tool supports TypeScript. Use `.js`, `.mjs`, or `.cjs` only when a verified tool/runtime constraint requires it. Generated `dist/` output is exempt.

## Source & Architecture

- Source lives under `src/`; generated `dist/` is never edited directly.
- `src/index.ts` is the sole supported plugin entrypoint.
- Public rule modules live in `src/rules/`; private shared implementation helpers live in `src/utils/`.
- Rule-page headers, option tables, fixability notices, and the README rule table are generated by `eslint-doc-generator`. Rule-specific behavior sections after the generated markers are maintained in the rule pages.
- Preserve observable rule behavior during extraction/refactoring unless behavior change is explicitly in scope.
- Prefer maintained upstream plugin rules for general-purpose invariants; add a Next Friday custom rule only for genuinely Next Friday-specific behavior.
- Keep runtime dependencies limited to shipped rule implementation needs. Repository tooling belongs in `devDependencies`.
- Public package boundaries and distribution requirements are documented in [`.agents/docs/architecture.md`](.agents/docs/architecture.md).

## Verification

Use the narrowest relevant check during iteration. Run `pnpm verify` before concluding package-wide changes. For dependency changes, also run `pnpm audit`. For public package changes, Publint and AreTheTypesWrong must pass.
